# 13\. Reliability and security engineering

Because this is an automated business, failures must be anticipated from the beginning.

| Potential failure | Engineering solution |
|--------|--------|
| AI API unavailable | Retry with exponential backoff and optional model fallback |
| Duplicate job execution | Idempotency keys and database constraints |
| Server restarts | Persistent queues, durable workflow state |
| Database and queue inconsistency | Transactional outbox and reconciliation |
| Invalid AI response | Schema validation |
| AI hallucination | Evidence requirements and independent review |
| Excessive AI expenditure | Per-job, per-product and monthly budgets |
| Malicious instructions in research pages | Treat external content as untrusted data; isolate tools |
| Duplicate product listing | Unique publication keys and remote reconciliation |
| Unauthorized publishing | Role-based access and approval gates |
| Data loss | Encrypted off-site database backups |
| High traffic | Rate limiting, caching and worker concurrency limits |

BullMQ specifically recommends designing jobs to be idempotent so that retries do not produce unintended duplicate effects. citeturn858177search0turn858177search12

AI-generated code or HTML must execute only through restricted, isolated environments.
